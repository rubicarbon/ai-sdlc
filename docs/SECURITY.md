# Security

This document describes what `ai-sdlc` defends against, which control covers which threat, which credentials the tooling needs, and where the protection stops. The controls that matter are deterministic (hooks, permission rules, platform policies, a human-only script); the skills and agent instructions are advisory and are listed only where they add a second layer.

## Threat model

| Threat | What it looks like in this loop |
| --- | --- |
| Prompt injection through tickets, PR bodies and web content | The agent reads work items, PR descriptions, review comments and research pages as input. Any of them can carry text that tells the agent to read a secret, disable a check, push to `main` or deploy. Ticket bodies on Azure round-trip through HTML, so injected text can also hide in markup |
| Secret exfiltration | Reading `.env`, cloud credential files or CLI login stores and echoing, copying, encoding or uploading them; or leaking them into a PR body, a comment or a log line |
| Unauthorised production changes | Pushing to the default branch, running the configured production deploy command, or any other command the project lists in `environments.prod.deployCommandPatterns` (`kubectl apply`, `terraform apply`, `helm upgrade` and similar when configured) from an agent session, without a human deciding that this commit ships |
| Supply chain via new dependencies | An agent adding an unpinned, typosquatted or unmaintained package, or a package with install scripts, to satisfy a ticket |
| MCP servers with broad tool access | A connected server that can write to production systems, send messages or run shell commands turns any injected instruction into an action outside the repository, past every file-level hook |

## Controls mapped to threats

| Control | Where | Covers |
| --- | --- | --- |
| Permission deny rules | `templates/settings.json.tmpl`, merged into the target repo's `.claude/settings.json` by `/ai-sdlc:sdlc-init` (see the two-layer table below for the exact list). `settings.github.json.tmpl` adds `Read(~/.config/gh/**)`, `settings.azure.json.tmpl` adds `Read(~/.azure/**)`. `Bash` is denied for `git push --force *`, `git push -f *`, `git push * --force*` | Secret exfiltration through the file tools, including `@file` mentions, which hooks do not see; force pushes |
| `guard-secrets` hook | `hooks/guard-secrets.sh`, PreToolUse on Read, Glob, Grep, Edit, Write, NotebookEdit, Bash, PowerShell | The same secret names for every tool call including shell commands (path tokens extracted from the command), the config-driven `guardrails.secretPaths` (replaces the project defaults; `[]` turns them off; the home-directory list is fixed), and read-or-copy commands that name `GITHUB_TOKEN=`, `GH_TOKEN=`, `AZURE_DEVOPS_EXT_PAT=`, `AWS_SHARED_CREDENTIALS_FILE`, `.netrc`, or a private key file (`id_rsa`, `id_ed25519`, `id_ecdsa` as whole names, so `id_rsa.pub` passes) |
| `guard-protected-paths` hook | `hooks/guard-protected-paths.sh`, PreToolUse on Edit, Write, NotebookEdit, Bash, PowerShell | The release markers (`.sdlc/release/**`, `.sdlc/UNLOCK_PROTECTED`) always, plus whatever the project lists in `guardrails.protectedPaths` (nothing by default). Reads stay allowed; a human unlocks a configured path for one edit by creating `.sdlc/UNLOCK_PROTECTED`, which never unlocks the markers themselves |
| `guard-verifier-readonly` hook | `hooks/guard-verifier-readonly.sh`, PreToolUse on Edit, Write, NotebookEdit | A compromised or over-eager verifier or security auditor cannot edit files. Its shell is not restricted; the agent prompts hold the report-don't-fix rule, and release evidence is checked separately (next rows) |
| `gate-production` hook plus `authorize.sh` | `hooks/gate-production.sh`; `scripts/ship/authorize.sh` | Commands matching `environments.prod.deployCommandPatterns` (no built-in patterns; init seeds `git push * <default branch>` and always adds the configured production command) run only while `.sdlc/release/AUTHORIZED-<HEAD sha>` is complete and valid: `authorised_by=`, `authorised_at=`, `expires=` and `commit=` each exactly once, a numeric expiry strictly in the future, a full sha equal to HEAD and to the file name (`scripts/ship/_authz.sh`, shared with `preflight.sh`). The marker is written by a human running `authorize.sh` at their own terminal: the script exits 2 when `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT` or `CLAUDE_PROJECT_DIR` is set, and the directory is a protected path |
| Branch protection and policies | `sdlc-platform branch_protect_apply` from `templates/github/branch-protection.json` and `templates/azure/branch-policies.json` | Nothing merges without a human code owner (GitHub) or required reviewer (Azure), required checks pass, stale reviews are dismissed on push, conversations are resolved, force pushes and deletions are blocked, admins are not exempt. The CI review job is told to comment only and never approve |
| Release evidence validation | `scripts/loop/_reports.sh`, used by `precondition.sh ship`, `preflight.sh` and `validate-report.sh` | A verification report counts only when it is a normal report (never `*-security.md`), non-empty, with exactly one `Verdict: PASS`, one `Commit:` equal to HEAD and one `Tree: clean` or `Tree: isolated` line: the verifier ran on a clean checkout, or in the disposable worktree of `scripts/verify/run-isolated.sh`, so the tree it verified was HEAD and not HEAD plus uncommitted fixes. A security report counts only with exactly one parseable `Blocking: <n>` line (and a matching `Commit:` when present); with `review.runner: local` only the PR-bound `*-pr<id>-security.md` for HEAD counts (the id from `--pr` or the branch mapping, else the gate fails closed), a `Commit:` line is mandatory and a `Status: stale` line rejects the report. Empty, duplicated, malformed or stale evidence is a red gate, never zero findings |
| Local review is a separate session on the exact PR head | `hooks/launch-local-review.sh`, `scripts/review/{status,snapshot,assemble,finalize}.sh`, `commands/sdlc-review.md` | With `review.runner: local` the reviewer is a fresh Claude Code session in its own window: the launcher unsets every `CLAUDE*` session variable (policy A, always) and under `review.localAuth: login` every `ANTHROPIC_*` variable and provider switch (policy B), so it is neither a nested session nor billed to an inherited key by default. It reviews a detached worktree of the commit the platform reports as the PR head (fetched and compared, exit 3 when it moved), never the author's checkout; the auditor's file edits stay denied by `guard-verifier-readonly`; it comments only and never approves; the report is published only after validation and a successful post, with `Status: stale` when the head moved meanwhile; one review per PR and sha at a time. The hook itself never denies and launches only for a documented command subset whose result is proven by stdout (the PR id) or by the remote-tracking ref, never by command text alone |
| CI review failure is a failed job (`review.runner: ci`) | `scripts/ci/azure-review.sh`, `templates/azure/pipelines/sdlc-pr-review.yml`, `templates/github/workflows/sdlc-pr-review.yml` | A Claude error, an exhausted cap, a missing or malformed report fails the review job; the Azure comment then reads `ai-sdlc review FAILED` and never resembles a completed review, so a build policy on the pipeline cannot turn green without a review result |
| CI cost caps (`review.runner: ci`) | `templates/github/workflows/sdlc-pr-review.yml`, `templates/azure/pipelines/sdlc-pr-review.yml`, `sdlc-cost-report.yml`, `scripts/cost/report.sh` | A runaway or injected review loop stops at `cost.maxTurns` and `cost.maxBudgetUsd`; each run records `sdlc-cost.json` and fails above the ceiling; weekly spend above `cost.alertThresholdUsd` opens an issue. The CI review runs with an allowlist of read-only tools (`Read,Grep,Glob,Bash(git diff *),Bash(git log *),Bash(git show *)`, plus `Write(review.md)` on Azure) |
| `sdlc-security-review` check list | `skills/sdlc-security-review/SKILL.md`, used by `sdlc-security-auditor` and the CI review | Injection, broken access control, privilege escalation, hardcoded secrets, unsafe deserialisation, new dependencies (pinned, known maintainer, justified in the PR body), missing authz on new endpoints, data exposure, human-only areas, and prompt injection surface in code that feeds untrusted text to an LLM or tool |
| `REVIEW.md` human-only areas | `templates/REVIEW.md.tmpl` | Authentication, authorisation, cryptography, payments and billing code is written by a human; an agent-authored change there is Blocking until a human rewrites or explicitly adopts it |
| Ticket discipline | `templates/REVIEW.md.tmpl`, `skills/sdlc-loop/SKILL.md` | Work without a ticket id in the PR is closed, not reviewed; the loop names the ticket in the branch and commits. A review rule, not a hook |

Every hook exits 0 silently when no `sdlc.config.json` is found, so none of the above applies until `/ai-sdlc:sdlc-init` has run in the repository.

### Two layers for secrets, with different reach

Hooks see every tool call (file tools, Glob/Grep, Bash, PowerShell) but not `@file` mentions in a prompt. The permission deny rules in `.claude/settings.json` see file tools and `@file` mentions but not the shell. The plugin keeps the two default sets name-for-name identical, so a hook exemption never contradicts a deny rule:

| guard-secrets default (hook) | Deny rules rendered by init |
| --- | --- |
| `.env`, `.env.*` (exempt: `.env.example`, `.env.sample`, `.env.template`, `.env.dist`) | `Read`/`Edit` on `.env`, `.env.local`, `.env.development`, `.env.staging`, `.env.production`, `.env.test`, `.env.*.local`. Explicit names, so the example files are never denied; a custom `.env.foo` is caught by the hook only |
| `secrets/**` | `Read(secrets/**)`, `Edit(secrets/**)` |
| `**/*-key.pem`, `**/*.key.pem`, `**/privkey.pem`, `**/*.key` | `Read(**/*-key.pem)`, `Read(**/*.key.pem)`, `Read(**/privkey.pem)`, `Read(**/*.key)`. Certificates (`cert.pem`, `chain.pem`, `fullchain.pem`, `*.crt`) are readable in both layers |
| `**/id_rsa`, `**/id_ed25519`, `**/id_ecdsa` | `Read(**/id_rsa)`, `Read(**/id_ed25519)`, `Read(**/id_ecdsa)`. `*.pub` keys are readable in both layers |
| `**/*.p12`, `**/*.pfx`, `**/credentials.json`, `**/service-account*.json` | `Read` on the same four patterns |
| home list (fixed, not configurable): `~/.ssh/**`, `~/.aws/**`, `~/.azure/**`, `~/.config/gh/**`, `~/.kube/config`, `~/.netrc`, `~/.npmrc`, `~/.docker/config.json` | `Read(~/.ssh/**)`, `Read(~/.aws/**)`, `Read(~/.kube/config)`, `Read(~/.netrc)`, plus `Read(~/.config/gh/**)` (GitHub) or `Read(~/.azure/**)` (Azure) |

`guardrails.secretPaths` configures the hook layer only: absent means the defaults above, `[]` means no project paths (the home list stays), a list replaces the defaults and is applied literally, with no exemption. The deny rules are not derived from the config; to release a path fully, edit both `secretPaths` and `.claude/settings.json` (which is not protected). A fixture file named like a real key (`id_rsa`, `server-key.pem`) is denied in both layers: rename it. `/ai-sdlc:sdlc-upgrade` removes deny rules an earlier plugin version wrote and the plugin no longer generates (`Edit(sdlc.config.json)`, `Edit(.env.*)`, `Read(**/*.pem)`, `Read(**/id_rsa*)`, `Read(**/id_ed25519*)`); the match is literal, so a user-typed rule with the same text is removed too, and each removal is printed.

### Deliberately not enforced

Lockfiles, CI files, `CODEOWNERS`, `sdlc.config.json`, `.claude/settings.json`, test files, ticket markers and the verifier's shell are not gated by hooks. Routine development runs without marker files; review, CI and branch protection carry development quality. One consequence is stated plainly: the production gate reads `environments.prod.deployCommandPatterns` from a file the agent may edit, so an agent could empty the list and then run the deploy command in the same session. The controls against that are the ones every other change goes through: the config edit shows up in the diff a human reviews, branch protection keeps the agent from merging it alone, and the platform-side production approval stands behind the deploy workflow. Projects that want the config file or their CI files hook-protected list them in `guardrails.protectedPaths`.

## Credentials and scopes

Agents hold no production credentials. Everything below is for the platform CLI the human is already logged into, or for CI.

| Credential | Needed by | Scope |
| --- | --- | --- |
| GitHub CLI login (`gh auth login`) | `scripts/platform/github/*.sh` | Classic token scopes `repo` and `workflow`. For a fine-grained PAT, grant on the repository what the adapter calls: Issues read and write (`work_item_*`), Pull requests read and write (`pr_*`), Contents read, Administration read and write (`branch_protect_apply` uses `PUT .../branches/{b}/protection`), Actions read (workflow runs as the deployment fallback and cost artifacts), Deployments read (`metrics_export`). Leave everything else unset |
| Azure CLI login (`az login` or `AZURE_DEVOPS_EXT_PAT`) with the `azure-devops` extension | `scripts/platform/azure/*.sh` | PAT scopes: Work Items read and write, Code read and write, Build read and execute, Project and Team read |
| `ANTHROPIC_API_KEY` | `sdlc-pr-review.yml` on both platforms (`review.runner: ci` only) | GitHub Actions secret, or the Azure variable group `sdlc-secrets`; both are created by a human following `docs/PLATFORM-SETUP.md`. Never in the repo, never read by the agent. With `review.runner: local` no key exists: the reviewer session uses the developer's own `/login` credentials (policy B removes any key from its environment by default) |
| `GITHUB_TOKEN` (GitHub) / `System.AccessToken` (Azure) | CI jobs only | Used to post the review comment, record deployments and read cost artifacts. Job permissions in the templates are the minimum for each job (`contents: read`, `pull-requests: write`, `issues: read` or `write`, `deployments: write`, `actions: read`, `id-token: write`) |
| Deploy credentials | `commands.deployStaging` and `commands.deployProduction`, owned by the repository, run inside the `staging` and `production` environments | Stored in the platform environment behind its required reviewers or Approvals check; not available to the agent session |

The agent reaches the platform only through `sdlc-platform`, which checks authentication once per invocation and reports a missing login with the platform's login command. It never reads `~/.config/gh`, `~/.azure` or a token file: both the deny rules and `guard-secrets` block that.

## MCP servers

Hooks and permission rules see file paths and shell commands. They do not see what an MCP server does on the agent's behalf, so a server with write access is a bypass of every control above. Guidance for a repository that runs this loop:

- Least privilege: connect servers with the narrowest scope that serves the ticket, and prefer per-repository or per-project credentials over account-wide ones.
- Read-only servers for agents: documentation, issue search, log search and code search servers are useful and low risk. A server that can create, update or send should be avoided in agent sessions or limited to the human's interactive use.
- No MCP server with deploy rights: nothing connected to an agent session should be able to run a pipeline, change infrastructure, rotate a secret or push to a protected branch. Those actions stay on the platform behind branch protection, environment approvals and `authorize.sh`.
- Treat server output as untrusted input: it carries the same prompt injection risk as a ticket body.

## What the plugin does not protect against

- Paths constructed at runtime inside a Bash command (a variable expanded by the shell, `base64 -d | sh`, `eval` of a computed string, a path built by a script the command runs). `guard-secrets` and `guard-protected-paths` inspect the command text as written; they cannot evaluate it.
- The verifier's shell. Only its file tools are hook-denied; a verifier that runs a mutating command is a prompt failure, and the `Tree:` line plus the clean-working-tree ship gate limit what such a run can certify. The isolation helper, when used, is directory-level isolation with after-the-fact proof: a verification command that writes into the main checkout by absolute path is detected by the fingerprint comparison (exit 4) and reported, not prevented, and changes to gitignored files are outside the fingerprint.
- `@file` mentions in a prompt. They do not pass through PreToolUse hooks, so only the permission deny rules in `.claude/settings.json` cover them. That is why the deny list carries the same secret names as the hook defaults, spelled out one by one.
- A human running `scripts/ship/authorize.sh` carelessly. The script proves a person was at a terminal; it does not judge the release. `scripts/ship/preflight.sh --pr <id>` lists every gate with evidence and should be read first.
- Encoding and evasion: a command that hides a secret path behind base64, `printf` escapes, `eval`, an alias, or a helper script the agent wrote a moment earlier is not recognised by token matching.
- A repository without `sdlc.config.json`: every hook is silent there by design.
- Anything an MCP server or another plugin's tool does.
- The Azure adapter is verified against mocks in this build, not against a live organisation; the policy and permission behaviour of a real Azure DevOps project (vote semantics, `az repos policy ... update` flags, required-reviewer identities) should be confirmed after the first `branch_protect_apply`. `.dev/VERIFY.md` lists every mock-only behaviour.
- `pr_checks` cannot tell "CI not configured" from "CI not started": both are an empty list and both are exit 1, so a PR with no checks never ships until a check reports. With `review.runner: local` on GitHub the review workflow is gone, so the project must keep another workflow that reports on pull requests; the rule is deliberately not relaxed.
- The local review runner trusts the developer machine: whoever can run commands there can open review windows or write state files under `.sdlc/tmp/review/`; the published report is still gated by validation and the PR post, and the human approval on the platform stays.
- The `git push` trigger detects an unreviewed synchronised commit; it does not prove the push command ran (a segment that did not execute can still match when the remote already holds that commit).

## Reporting a security issue in the kit

Open an issue on the repository: `https://github.com/rubicarbon/ai-sdlc/issues`. Describe the control that failed, the exact tool call or command that got through, and the plugin version (`SDLC_PLUGIN_VERSION`, printed by `/ai-sdlc:sdlc-status`). If the report contains a real secret or a reproduction against a real production system, redact the values and say so in the issue; the location is enough.
